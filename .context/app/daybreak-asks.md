# Daybreak asks — Reclaim Your Week → Daybreak

The leaf-tier sibling of Daybreak's own
[`upstream-asks.md`](../framework/upstream-asks.md), one tier down. Two kinds of
row live here:

- **Fork-first seams** — framework-tier code this app carried because the seam it
  needs does not exist in Daybreak yet. `upstream`'s push URL is disabled, so the
  change lives here until Daybreak adopts it. On every Daybreak pull
  (`git fetch upstream && git merge upstream/main`), check each **open** row: if
  Daybreak has landed it, **delete our copy and delegate**, then close the row.
- **Defects** — framework bugs this app found by being Daybreak's first real
  consumer. That is a stated goal of this build, not a side effect: F3
  (`ryw-firstlight`) budgets two to three, and anything the build trips over
  afterwards belongs here too.

Without this ledger, a framework-tier change we carry either conflicts on the
next sync or quietly becomes permanent local divergence. That is the whole reason
the tier below keeps the same file.

**This is not a boundary-breach log.** A breach is editing a Daybreak-owned file
because no seam exists — those get a minimal `keep-mine` edit and a follow-up, per
the [`CLAUDE.md`](../../CLAUDE.md) banner. This ledger is the sanctioned case: the
code is clean framework-tier work whose final home is upstream.

## Adding a row

1. Add the row (our change or the defect, the owning feature, the concrete
   delegate/fix action, status).
2. File it against **the tier that owns the code**, as the feature's own Done-when
   deliverable — a fork-perspective note on an existing issue if one tracks it,
   otherwise a new one. **Framework-tier** asks (`lib/framework/**`, the boot/seed
   chain, journey engine) go to **Daybreak**
   (`human-centric-engineering/daybreak`). **Sunrise-core** asks (core `lib/`,
   `app/api/v1`, orchestration/chat, `components/**`) go to **Sunrise**
   (`human-centric-engineering/sunrise`, label `upstream-gap`) — they reach us
   _through_ Daybreak, but the fix lands in the tier that owns the file, so file it
   there directly.
3. Close the row on the pull that lands it, once our copy is deleted and callers
   delegate.

## Closing a row

There are **three** ways a row closes, not one. The third is the one that gets
skipped, and skipping it is how a ledger grows forever:

1. **Adopt** — upstream landed it, our copy goes, callers delegate. The default,
   and what step 3 above describes.
2. **Adapt** — what shipped is right but not shaped like our workaround, so we
   change our code to meet it. Often the change is a **comment**: a condition
   whose stated reason has expired is what the next person deletes during a
   tidy-up, so re-anchoring the reason is real work, not bookkeeping.
3. **Won't-adopt** — upstream landed something reasonable that this app should
   not consume, usually because the ask was **wrong about our own needs**. Close
   it with that reasoning written down. Leaving it open against a fix that already
   shipped is worse than closing it: the next reader treats a settled decision as
   outstanding work.

**File a _new_ issue only when the gap is generic, still unmet, and we would
actually use the fix.** All three, not two. Filing for something we will not
consume produces an issue nobody can prioritise against real demand — and a gap
we noticed but have no use for belongs in the row's prose, flagged as a
good-citizen contribution, not in the tracker as an ask.

[`upstream-sync-2026-08.md`](./upstream-sync-2026-08.md) §C4 (won't-adopt), §C7
(adapt), §C11 (keep ours, and why ownership beats duplication).
